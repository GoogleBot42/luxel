# Tools directory

One-page index of every script and harness in the repo. Each file carries
its full usage in a header comment — this page exists so you know what to
open. Everything runs inside `nix develop` from the repo root unless noted.

Most of these drive a device or the mirror over HTTP; the routes they call
are documented once in [docs/api.md](api.md), not here.

## CI

| tool | what it does |
|---|---|
| `tools/ci.sh` | **The CI gate** — the exact sequence `.gitea/workflows/ci.yml` runs on every push to master and every PR, in one script so you can run the same thing locally: `nix develop --command tools/ci.sh`. Four steps in a load-bearing order: the web build + `npm test` (which since #592 also packs the bundle and fails if it does not fit the 983,040 B assets partition — it prints the headroom every run), `cargo test --workspace`, `tools/check-library.sh`, then the firmware half, which is two things since 2026-09-08 (Gitea #413/#438): a devshell `firmware/build-esp32.sh` for `CI_BOARD` (default `board-pixelblaze-v3`) with `tools/image-check.sh` over its ELF (linked-feature markers — this is what keeps `build-esp32.sh` itself covered), and then `nix build .#luxel-fw-<variant>` + `tools/image-check.sh` over the **release image** for `pixelblaze-v3`, `c6-devkit-hosted` and `c3-devkit` (markers **and** the OTA-slot margin — per board since Gitea #501, or the old 1 MiB slot when `MIGRATING_RELEASE=1` is set — opt-in since Gitea #635, `ci.sh` defaults it to 0). Three variants because one board was not enough: on 2026-09-07 the C3 stopped compiling (Gitea #413) and the shipped C6 image fell under the 3 % floor (Gitea #438) and both merged green, since the eight-image matrix only runs at a `v*` tag. The **flake** image because a devshell one is not the artifact that ships: it bakes the dev WiFi creds, whose length moves the number, and CI's placeholder `creds.env` is not the release build's. (It *used* to additionally embed every dependency's absolute source path in its panic `Location`s, reading ~2.8 KB larger and by a different amount on every machine — which against a 3 %-of-1-MiB floor decided pass/fail by checkout path length. Gitea #441 fixed that at the source; the two builds now agree to ~160 B, which is still not a reason to gate the wrong artifact.) Web first because `luxel-cli`'s `heapstat` test reads `web/public/gallery.json`, which the web build writes. Must run from inside the devshell, entered at the repo ROOT (the shellHook materializes `firmware/vendor/esp-hub75` relative to the shell's cwd). `CI_SKIP="web cargo library firmware"` drops steps while iterating; `CI_BOARD` picks the devshell board and `CI_VARIANTS` the release images to check (release.yml's spelling, e.g. `c6-devkit-hosted`; `CI_VARIANTS=` skips that half). A fifth step, the QEMU suite (`tools/qemu/run-all.py`), is **opt-in** behind `CI_QEMU=1` and is NOT part of the hosted gate: it wants a from-source build of Espressif's QEMU fork and five of its thirty tests need the gitignored Athom dumps, which CI does not have (they skip there; the twenty-two #501/#634 migration tests compose their own flash and do not). Run it locally — `CI_QEMU=1 CI_SKIP="web cargo library firmware" nix develop --command tools/ci.sh`, ~95 s warm — before merging anything under `firmware/src/{takeover,migrate,parttab,ota,flashmap}.rs` or either `partitions*.csv` (Gitea #273/#501/#634). Not a device tool and no substitute for the hardware gates below — it has no device, no browser e2e and no soak. |

## Device operations

| tool | what it does |
|---|---|
| `[BOARD=…] tools/deploy.sh <ip> [--fw-only\|--assets-only]` | The one-shot deploy: builds firmware + web app, OTAs the image (waits for the reboot), streams the asset archive. The board comes from `$BOARD` (default `board-pixelblaze-v3`) and is exported to `ota-push.sh`, which verifies the image really is that board's build; `$1` is the device address, never the board. Serial flashing does NOT update assets — use this after any serial recovery. Against a `hosted-ui` device (docs/boards.md) the asset half refuses with an explanation; use `--fw-only`. **`tools/deploy.sh --package <out.luxr>`** pushes nothing: it builds both halves and writes the `.luxr` release package (Gitea #643) the release workflow publishes and the console installs — same packer, so the bench and CI agree. |
| `[BOARD=…] tools/ota-push.sh <ip> [image]` | Just the firmware OTA + comes-back-on-the-new-slot verification (deploy.sh calls it). Refuses images built without WiFi creds. With no image argument it saves one from the devshell build for `$BOARD` (default `board-pixelblaze-v3`) through `firmware/board-target.sh`, so the ELF path and `espflash --chip` follow the board — pass `BOARD=` for anything that isn't the classic ESP32 or it looks for an ELF that build never produced. It also **refuses an image that isn't a build of `$BOARD`**: every image bakes its `board::NAME` in as a plain string (`board_name` in `firmware/board-target.sh`), and the three classic-ESP32 boards share one ELF path, so a stale build of another board otherwise pushes cleanly and differs only in `RESERVED_PINS` / pin defaults — Gitea #389 put a pb-v3 image on the Athom, which reserved GPIO18, the pin the strip is wired to. An image given as `$2` is checked only when `$BOARD` is set explicitly (a nix-built `result/luxel-fw-ota.bin` carries its own board); `SKIP_BOARD_CHECK=1` opts out. |
| `tools/decode-backtrace.sh` | Symbolicate ESP32 panic backtraces from a serial log against the current ELF. Symbol names only — `[profile.release]` sets no `debug`, so there are no line tables and `addr2line` answers `luxel_fw.<hash>-cgu.0:?` for the file. The file and line you actually want are in the panic message itself, which since Gitea #441 names a dependency source relative to its registry/vendor root (`esp-hal-1.1.0/src/system.rs:42`). |
| `tools/release.sh [X.Y.Z] [--dry-run]` | Cut a release tag (validates tag == firmware/Cargo.toml on origin/master, then tags via the Gitea API). The GitHub mirror's release workflow builds + publishes the assets — see docs/releases.md for the whole pipeline. |
| `firmware/serial.log` | Live serial feed from the dev unit (fed from outside the container — there is no in-container serial). Watch for `PANIC` / `panic: rebooting in 3s` / `pattern rejected`; the HTTP-side view of a soak hides reboots (the device is back in ~5 s and retries succeed). |

## Hardware verification

| tool | what it does |
|---|---|
| `tools/hw-bench.mjs <ip> [report.md]` | **The soak**: pushes all ~320 gallery patterns to a real device one by one (**45 min–2 h**; each pattern costs a flash slot write, so the wall clock tracks the device more than the pattern count — the Athom took ~2 h for 303 patterns on 2026-08-31, and the "15 min" in older notes predates the gallery doubling), samples fps/heap/vmerr per pattern, then measures fps vs pixel count (60→2048), restores the device, and writes `docs/bench-report.md`. The definitive "does the firmware survive real patterns" gate — run it with a serial-log monitor for panics. A device that goes unreachable after a push is recorded as a **crashed** row (not an abort — the 2026-09-05 Seengreat run died at pattern 75 with no report before this): the harness waits up to 3 min for it to return and, after 90 s, runs `HW_BENCH_RESET_CMD` if set (for the S3's native USB, `timeout 3 socat -u /dev/ttyACM0,raw,echo=0,b115200 STDOUT` — the termios setup IS a reset there). `HW_BENCH_FROM=<n>` resumes at gallery index n; the report is written even if the curve/restore phase fails, and its summary counts the crashes. It restores the pixel count, brightness and pattern it found (it used to hardcode a 300 px restore; fixed 2026-08-30). **The sweep runs at whatever count the device was already on** — the report header and its fps line say which, and rig shape is load-bearing, so read that line before concluding anything about a pattern that failed (Gitea #193 was chased at 300 px for a bug that only bites at 60). |
| `tools/hw-bench.mjs <ip> [report.md] --perf-only` | **The perf sweep** (same push/sample loop, no stability phases): 3 s per pattern, no pixel-count curve, and the report is one row per pattern — fps plus the per-stage timers `frame/vm/pipe/out` (Gitea #260) and heap — **sorted by vm µs, worst first**, with the median/p90 of the distribution in the summary. This is the baseline the interpreter work is measured against (#261 superinstructions, #265 two-core split): re-run it after an engine change and diff the table, don't re-derive it by hand. Latest run: `docs/perf-sweep-s3.md` (Seengreat 64x64 panel, 4096 px). |
| `tools/render-bench.mjs <ip> [--px 60,2048] [--runs 3] [--dwell 5]` | **The render-core benchmark** (Gitea #259/#260): at each pixel count pushes rainbow, `library/snake.js` and `library/snake-2d.js` (Smartness raised to 100 — the intensive variant), samples fps + heap, then downloads the playground bundle (`/assets/index-*.js`) a few times WHILE the pattern runs and reports the median wall time — the "does rendering starve the web server" number. Prints a markdown table; restores the pixel count it found and rainbow; never touches brightness. ~2 min per pixel count. Needs `npm run wasm` once (lxp.mjs). |
| `tools/ringsim.py` | **Descriptor-ring state simulator for the HUB75 atomic swap** (Gitea #395, run `python3 tools/ringsim.py`). Models the GDMA walking the two 254-descriptor rings, `swap()` arming a flip by rewriting the running ring's tail `next`, and the frame-count ISR landing it and restoring the old tail — one tick per descriptor, over random request phases. Asserts the invariant the hardware counter checks: `suc_eof` sits only on a ring's last descriptor, so every EOF-to-EOF interval must be exactly one ring. Finds zero short passes across prefetch depths 1-8, ISR latencies to 300 ticks, and no safety margin; and shows what the mechanisms that *could* truncate a pass look like instead — a DMA restart gives LONG passes, a ring rebuilt under the engine gives neither. Use it to test a change to the swap/landing logic before it goes near the panel, where a wrong answer costs a reflash. |
| `tools/panel-load-bench.mjs <ip> [--idle SEC] [--tab SEC] [--busy SEC] [--clients N] [--label NAME] [--out FILE]` | **Does web/net load steal the panel's compose window?** (Gitea #395/#329). With vsync the HUB75 compose must finish inside one rescan (8.7 ms at 30 MHz), so any core-0 handler that runs longer than the leftover slack pushes the swap past the wrap and the panel rescans the previous frame again (a REPEAT, the artefact left after #376/#387). Runs three phases against the same build: **idle** (status every 10 s, nothing else), **tab** (ONE playground tab — 1 Hz `/api/status` + `/api/patterns`, the realistic case), and **busy** (N clients looping `/api/patterns` + `/api/status` + the playground bundle). Reports **repeats/min exact** — the start/end delta of the driver's own `pass.repeats` ISR counter (#398), so it is independent of the sampling rate — plus the repeat share of all passes, the older `rescan_hz − out_fps` integral (kept so a comparison against a pre-#398 build still has a common column), `pass.skips`, `dropped`/`eof_race`/`slow_path` deltas, `/api/status` latency p50/p95/max, load-request latency and throughput, heap floor, `fence_timeouts`, and a reboot check. `0` disables a phase. **Use `--clients 1`**: 3 clients looping the bundle saturate the 3-socket web pool so completely that the sampler's own `/api/status` is refused and the busy phase yields no data at all (Seengreat panel, 2026-09-07). The bundle path is discovered from the served index, so a rehashed build does not break it. **GET-only — it never writes to the device.** Run it twice, `--label before` on master and `--label after` on the change, and diff. |
| `tools/opbench.mjs <ip> [--k 0,50,100,200] [--pixels N] [--mhz F] [--json out.json] [--label T]` | **The per-op interpreter cost** (Gitea #312): pushes a synthetic pattern whose `render` runs a K-iteration loop of `x += i * 0.5`, sweeps K, and fits the SLOPE of `vm_us` against K — which cancels the wire, the per-pixel VM entry, `beforeRender` and the frame pipeline, leaving pure dispatch. Prints µs and cycles per loop iteration and per bytecode op, with the fit's r². **Ops per iteration are measured, not assumed**: it builds `luxel` with `--features profile` and takes the slope of `insns/px` over the same K sweep, so a compiler change that alters the fused stream shows up in the same run. Report BOTH numbers for any engine change — ops/px × cycles/op is the thing that matters, and they can move in opposite directions. Runs at 256 px by default (K=200 at 4096 px would be a 4-second frame) and restores the pixel count it found plus rainbow. **Match the device's own regime**: 256 px on the Athom (comparability with the PB oracle), but on the 64x64 panel pass `--pixels 4096 --k 0,10,20,40` — at 256 px it is pacing-capped at 125 fps and the cache behaviour under a full-panel frame is exactly what an engine change is being judged on. ~4 min. Needs `npm run wasm` once (lxp.mjs). |
| `tools/patbench.mjs <ip> <pattern> [--pixels N] [--samples N] [--settle MS] [--repeat N] [--json PATH]` | **The per-PATTERN VM cost, and the reason `opbench.mjs` is not enough on its own** (Gitea #318). Pushes one `library/` pattern, settles, and reports the median `vm_us` and `vm_us/px` from `/api/status`. `opbench` measures the dispatch loop in isolation; this measures what a pattern actually costs, and the two can point in OPPOSITE directions: inlining the fused const-arg arms' `binop_const` was **−7.5 % on the loop microbench and +38 % on a noise-heavy pattern** on the Athom, because `Vm::run` growing pushes the 21 KB `call_builtin` out of what stays resident in the flash instruction cache — and the effect is not even monotonic in size, it is layout. Conversely the #325 debug-check change read −4.5 % on the loop and **−46 % here**. Run BOTH for any luxel-core change. **Pick a stateless pattern**: `snake-2d` and friends carry game state whose per-frame work varies, which makes them useless as an A/B probe; `perlin-fire-wind-tunnel` is a pure function of time and coordinates and repeats to ±0.3 % on the Athom. Restores the pixel count it found, running rainbow. **Measure each device at its native pixel count** — `--pixels 4096` on the 64x64 panel, not the 256 px default: at 256 px the panel is frame-pacing-capped and the per-frame HUB75 compose is amortised over 16x fewer pixels. Say which pixel count each row used when comparing devices. ~1 min per repeat. Needs `npm run wasm` once (lxp.mjs). |
| `tools/wire-check.sh <device-ip-or-url>` | curl-level contract check of the device HTTP surface (single Content-Type per response, Content-Length == body bytes incl. the flash-streamed routes, asset 200/304 caching headers, all four OPTIONS preflight headers, 404 shape). Run after any `firmware/src/server.rs` change lands on a device (see `.claude/rules/firmware.md`'s one-`Reply`-type rule, Gitea #167). Plain bash+curl, no devshell needed. Takes `192.168.0.183` **or** `http://192.168.0.183` — the URL form used to build `http://http://…`, and with curl silenced every capture came back empty and every check FAILed against a healthy device (Gitea #346). Exit codes separate the three outcomes: **0** all pass, **1** a real contract FAIL, **2** `HARNESS BROKEN` (a capture never landed — never a firmware verdict), **3** `DEVICE UNREACHABLE`. |
| `tools/improv-provision.mjs <port> <ssid> <pass>` | Puts a stock/restored WLED (0.13+) onto the LAN over Improv-serial — one UART packet, zero button holds; WLED persists cfg.json + wsec.json so takeover credential inheritance works afterwards. `stty -F <port> 115200 raw -echo` first, and stop any serial capture (single-reader rule). Prints the device URL from WLED's reply. |
| `tools/store-audit.mjs <ip> verify\|fill\|churn <pattern>\|wipe [--pin <name>] [--rounds N] [--hammer] [--quiet]` | **The pattern-store auditor** (Gitea #379): drives the packed file log over the public API and re-checks the **full name set after every single save and delete** — `expected = previous + saved - deleted` — instead of counting at the end. That is the invariant that catches a compaction dropping files, which is exactly how #379 hid: every save answered `{"ok":true}` while the count went *down*. It also checks the packing arithmetic (a non-compacting save must grow `store.used` by **exactly** `48 + align4(name) + align4(source) + align4(bytecode)`, a delete must move that same number into `dead`) and reports each compaction's wall time and the `dead` residue it leaves — 0 with nothing pinned, a sub-page hole when something is. `churn --pin <name>` activates a stored pattern first so the compaction has to route around its frozen pages (run it with the lowest-offset, a middle and the highest file to cover the placement cases); with no `--pin` an ad-hoc `/api/code` push runs, so nothing is pinned. `--hammer` keeps a concurrent `GET /api/patterns/<id>` going across every save — a compaction must never serve a truncated body. Exit 1 on an audit failure, 3 if the device is unreachable. Needs `npm run wasm` once (lxp.mjs). **`wipe` and `fill` are destructive** — they are for a rig, not for a device whose library someone wants. |
| `tools/event-soak.mjs <ip>` | Focused soak of external event injection (`POST /api/events` → `readEvent`): live-codes a counter pattern, injects ~30k events (steady 1–32 batches, malformed frames, 32-batch overflow bursts), verifies delivery/rejection/heap/fps over HTTP only (`/api/vars` is raw 16.16). Requires firmware **>= v0.1.39** (a minimum check — it used to hard-fail on anything but exactly v0.1.39). First run 2026-08-22 on the Athom: all green. |
| `tools/rx-stress.mjs <ip> [secs] [px]` | **The WiFi RX-pool gate**: floods the device with DDP frames (~245 pkt/s × 300 px ≈ 220 KB/s inbound UDP) while 6 HTTP workers hammer the API, watching heap/vmerr/`slot` at 1 Hz. Required before touching `static_rx_buf_num`/`dynamic_rx_buf_num`/`ampdu_rx_enable` — esp-radio's allocations don't null-check, so an undersized pool is a StoreProhibited panic, not an error. Run a serial capture alongside it. Sets the pixel count for the run and restores what it found. |
| `tools/soak.mjs [rounds] [dwell-ms] [--device <ip>] [--limit <n>]` | The host-side twin: same pattern-churn against `luxel serve` (the native mirror) — liveness/fps/memory without hardware. `--device <ip>` points the same churn at a real device instead (no RSS sampling). Patterns come from `corpus/*.epe` when the gitignored corpus is present, else from `web/public/gallery.json`, so a fresh worktree can soak too. Uploads are LXP1 envelopes compiled locally via `web/tools/lxp.mjs` (needs `npm run wasm`), and the run **exits 1** if under half of them are accepted — an all-rejected run tests the envelope validator, not the engine (Gitea #218). |
| `[BOARD=…] [EXTRA_FEATURES=…] tools/stack-check.sh [budget]` | Builds the firmware with `-Z emit-stack-sizes` and fails if any function's stack frame exceeds the budget (default 12 KB), or if the leftover `.stack` drops below 24 KB. Sees EVERY linked function incl. deps — catches what clippy's lints can't. `stack-check.py` is its ELF parser. Works for any board (default `board-pixelblaze-v3`); chip/target/toolchain come from `firmware/board-target.sh`, the shared board map that `firmware/build-esp32.sh` also sources. `EXTRA_FEATURES=small-chip` checks the RAM-constrained profile, which shifts the statics/stack split and so needs its own run (same env knob as `build-esp32.sh`). It also applies the board's `IRAM` feature list, which is the whole point on the S3 and the C-series, where `.rwtext` and `.stack` are the same SRAM — `IRAM_OFF=1` measures the other side (Gitea #328, docs/boards.md "IRAM budget"). Like `build-esp32.sh` it exports `RUSTFLAGS` (link args + the #441 `--remap-path-prefix` set, both from `board-target.sh`), which outranks `.cargo/config.toml` **and** `CARGO_TARGET_<TRIPLE>_RUSTFLAGS` — add one-off codegen flags with `EXTRA_RUSTFLAGS=…`, which is appended, not through the per-target env var, which is ignored here. |
| `tools/size-report.py` | Flash-size breakdown of the firmware ELF (see docs/size-report.md for the methodology + history). |
| `tools/qemu/qemu-espressif.nix` (`nix build .#qemu-espressif`) | Flake-output Nix derivation for Espressif's QEMU fork (esp32 machine, flash-file backed), carrying the patches that make esp-rs firmware run (`tools/qemu/patches/` + a `postPatch` block): CPENABLE reset on both machines, DPORT `INTR_STATUS`, TIMG level-int gating, and — since Gitea #634, which is what got the 16 MB S3 image running — the esp32s3 machine's BBPLL calibration-done bit, its APP-CPU stall (`SYSTEM_CORE_1_CONTROL_0`), three divide-by-zero SIGFPEs in the shared C3/S3 timer-group model, and a bound on MMU page writes that used to SIGSEGV QEMU on a 16 MB part. Each patch file opens with what breaks without it. Stock images boot to the WiFi task — see docs/research/qemu-emulation-spike.md for the CLI and the divergence notes. |
| `tools/qemu/takeover-test.py --stock <stock.bin> --fs <fs.bin> [--slot app0\|app1]` | **The WLED→Luxel takeover test, hardware-free.** Composes a 4 MiB flash in the exact state a real Athom is in when WLED's OTA updater has just accepted a Luxel upload (stock dump + configured WLED littlefs at 0x310000 + `result/luxel-fw-ota.bin` in an app slot + an otadata entry selecting it), boots it under the patched QEMU, and asserts the takeover's serial narration **and** the resulting flash bytes (Luxel table at 0x8000, `LXCF` inherited-creds record, the copied image, untouched littlefs, otadata/boot-guard state). `--slot app1` (default) exercises the full 920 KiB self-copy; `--slot app0` the skip-the-copy path; `--inject-fault` drops boot 1's program ops at sector 0x10000 via the emulator's m25p80 fault-injection patch (`LUXEL_FLAKY_WRITE`) and asserts the takeover's bounded reboot-to-retry recovers (issue #35). `--wled-pin N` rewrites `hw.led.ins[0].pin[0]` in the littlefs fixture before composing (a same-length byte poke into a CTZ data block, which carries no CRC) so the one dump covers all three arms of the data-pin decision: the dump's own GPIO18 **is** the Athom's `DEFAULT_DATA_PIN`, so unrewritten it only proves the takeover stores no redundant override; `--wled-pin 19` proves the import, `--wled-pin 10` the this-board-reserves-it refusal (Gitea #154/#273). Since #501 the table it installs is the repartitioned 4 MB one, so the post-takeover assertions are derived from THAT layout: `storage` is 0x290000, which sits **above** the end of WLED's app1 image, so the whole 0x190000 copy source now survives byte-for-byte (before the repartition that assertion had to stop at 0x210000 and assert the reclaimed tail separately), and the test instead checks that the pattern store formatted the key area at 0x290000. ~5 s / ~2 s / ~6 s. Needs `nix build .#luxel-fw-athom-music` first and the two **gitignored** dumps `athom-wled-stock.bin` / `athom-wled-fs-configured.bin` from the main checkout — local/agent harness, not CI. |
| `tools/qemu/migrate-test.py [--board athom\|s3] [--from ota_0\|ota_1] [--cut copy\|staged\|stored\|assets] [--overfill] [--old-bootloader 4mb] [--reflash-bootloader 16mb] [--plan-16mb]` | **The #501 partition-migration test, hardware-free and dump-free.** Composes a flash in exactly the state a field device is in when it finishes receiving the migrating release — a hand-built **pre-#501** table at 0x8000 (1 MiB OTA slots, `storage` 0x210000), LXCF/LXDV nvs records so the device is *configured*, a synthetic LUX2 bundle in `assets`, and a realistic `storage` partition from `tools/storegen` — boots it, and asserts `migrate.rs`'s narration **and** the resulting bytes: the new table at 0x8000, ota_0 == `luxel-fw-ota.bin`, `assets` byte-identical across the whole run (the 4 MB layout's entire point), nvs NOT wiped (unlike the takeover), otadata reselected to ota_0, and — through `storegen verify` — every reserved blob and every live pattern present in the relocated store with byte-identical source and bytecode and no dead records. The encoder that builds the old table is itself checked: the same code builds the NEW table and must byte-equal the merged image's own 0x8000 sector, which espflash wrote with `esp-idf-part`. `--from ota_1` exercises the self-copy + extra reboot (it is the case that caught the overlap guard comparing against the destination *slot* length instead of the copy length, which refused every ota_1 device); `--cut <stage>` kills QEMU mid-migration — on a serial line for `copy`, on a **flash-file watermark** for the rest, because the gaps between the later lines are microseconds — then re-runs on the same flash and asserts the `LXMG` staging header resumed it correctly (the expected resume stage is **read off the flash**, not inferred from the flag) and every byte still checks out. `--cut assets` aims at the narrowest window in the migration — the two sector cycles between the store move being recorded and the table write — which a 1 ms Python poll wins only about half the time, so it recomposes and retries up to `--cut-attempts` (default 6) rather than either flaking or widening into a different test; `--overfill` asserts the refusal leaves the old table and the old store untouched; `--board s3` runs the whole thing again over `firmware/partitions-16mb.csv` on QEMU's **esp32s3** machine with a 16 MiB image from `.#luxel-fw-seengreat-hub75` — the only layout whose `assets` partition MOVES, so the only one that executes `migrate::move_assets`' copy branch (asserted byte-identical at 0xa10000). That machine used to load the app and print nothing at all; five emulator bugs in `tools/qemu/patches/` (a BBPLL calibration-done bit that never sets, a free-running APP CPU, three divide-by-zero SIGFPEs in the timer-group model, an unbounded MMU page write that SIGSEGVed QEMU on a 16 MB part, and the CPENABLE reset value) are what changed, guest-side untouched per CLAUDE.md's isolation rule. `--old-bootloader 4mb` stamps the composed image's **bootloader** header with a smaller flash size — a device serially flashed before its table grew, which is exactly what the Seengreat is (Gitea #634): `g_rom_flashchip.chip_size` comes from that header, an OTA never replaces the bootloader, and the ROM bounds-checks every flash op against it, so a 16 MB table's `storage` erase at 0x610000 would fail on its first sector. Since #634's second half the device does not refuse — it migrates to the **largest embedded layout that fits under the ceiling**, i.e. `partitions.csv`, through the identical code the Athom ran — so the case asserts the full 4 MB migration on a 16 MiB part plus the every-boot `upgrade_available` narration, and works with `--from`/`--cut` like any other. `--reflash-bootloader 16mb` then restamps that same header on the SAME flash and boots again — Jeremy's one-time serial re-flash — and asserts the device migrates a **second** time, 4 MB layout → 16 MB (store 0x290000 → 0x610000, bundle 0x310000 → 0xa10000 byte-identical, staged in the 4 MB layout's ota_1 at 0x150000), which is what proves `migrated:true` never means "stop looking". Then an **`arrayReplace` fill lint** (Gitea #225): `arrayReplace(a, v1, v2, …)` splats its value list from index 0 — one value writes one slot — so the two-argument `arrayReplace(a, 0)` zeroes `a[0]` and leaves the rest of the buffer alone. Read as a fill (which is what the playground docs claimed until 2026-08-31) it silently freezes buffer-based patterns: an accumulation buffer that never clears saturates to a static wash, a "reset" resets nothing, and nothing errors. Any two-argument call fails the sweep, naming file:line and the replacements — `feedback(a, 0)` to zero, `arrayMutate(a, (v) => c)` to fill, `arrayReplaceAt(a, i, v)` for one element. Mentions inside `//` comments, `arrayReplaceAt`, and longer identifiers ending in `arrayReplace` are not flagged; a deliberate single-slot splat opts out with a trailing `// arrayReplace-2arg-ok` comment (no site in `library/` needs one today). `corpus/` has its own richer harness below. |

## CLI (`cargo run -p luxel-cli --` or `target/release/luxel`)

`run` (PPM frame strip) · `bench` (VM throughput) · `parse` (AST dump) ·
`check` (compile + bytecode round-trip + smoke, JSON line — the corpus
report's engine) · `compile` (source → `.lxbc`) · `pixels`/`vars` (oracle
halves) · `serve` (the native device-API mirror the web e2e runs against —
route reference in [docs/api.md](api.md)).

`serve` impersonates a device it is not, so UI work that gates on device facts
can be driven without that hardware: `--heap-free`/`--engine-heap` (the
editor's capacity warning), `--fps`/`--out-fps`/`--rescan-hz` (a pipelined
panel's frame rates), and **`--board strip|panel` / `--outputs N`** (Gitea
#464) — `--board panel` reports `max_pixels` 4096, comes up on its own 64×64
grid and advertises panel `caps` (`panel:true`, `strip_driver:false`,
`power_cap:false`, `layers:2`), which is what the v2 Settings page's
capability gating reads — and it now comes up with the matching Layout
(`kind:"matrix"`, 64×64, 4096 px) rather than a 300 px strip wearing a panel's
map. It is the flag form of what `web/tools/maxpixels-e2e.mjs` does by
intercepting `/api/status` in the page.

`--pixels N` past the run's ceiling is a **hard error** naming the ceiling, not
a silent clamp (Gitea #495 — the clamp is what quietly disarmed device-e2e's
#420 element-ledger check, and a `grid 64 64` posted to a clamped 2048 px
mirror was truncated to 2048 coordinates, which `detect_grid` then reported as
a 64×32 grid rather than the 64×64 asked for). `--max-pixels N` raises or
lowers that ceiling explicitly, which is how a strip mirror is driven at a
panel's pixel count without impersonating a panel; `--board panel` is the other
route when you want the panel's capabilities too.

`--scenes FILE` seeds the mirror's scene store from a file of wire blocks
(Gitea #478) — the flag a harness reaches for to bring a mirror up with
scenes already in it; the store, like the text slots, is in-memory only.

`--ddp-port` / `--e131-port` move the network-input listeners off the standard
DDP 4048 / sACN 5568 (Gitea #496). Those ports are global, so a mirror left
running by another session owns them for everyone; the e2e harnesses give the
mirror under test this run's own pair and pass `0` (an ephemeral port) to every
other mirror they start.

`run`/`bench` also take `--proj MODE` (`index|x|y|z|xy|xz|yz`, Gitea #473) —
the projection for a pattern whose dimensionality differs from the rig's. It
sets the slot matching the pattern's own dims and prints what the engine
resolved (`1D pattern on a 2D rig → x (pixelCount 64)`) to stderr; a mode the
pair doesn't offer falls back to that pair's default, and a pair with no
options at all — a rig smaller than the pattern, which since Gitea #538 is
never projected — prints `native`. `bench --map-grid 64x64
--proj x` is the way to measure the along-axis saving: `library/snake.js`
1000 frames goes 0.231 s → 0.009 s, `library/1d-aurora-borealis.js` 1.40 s →
0.032 s (64 render calls instead of 4096, plus a replicate pass). Table:
[docs/spec/projection.md](spec/projection.md).

`run <pattern> --map-grid WxH --out frames.ppm` is the equivalence harness for
a pattern rewrite: render before and after, diff the PPMs (`--map-grid` is
missing from the CLI's own usage line, and is **space-separated only** —
`--map-grid=16x16` exits 2 as an "unknown option", which in a two-run diff
just leaves the previous `--out` file in place and reads as a real pixel
difference). Gotcha: a cell's own `cx/(W-1)` is NOT the coordinate the engine
hands `render2D`. `MapData::coord` is `round(c * 65535 / (W-1))`, which equals
the naive divide only where `65535/(W-1)` divides evenly — 16 does, 64 and 17
do not (11 of 64 columns and 8 of 17 disagree) — and even then the far edge
normalizes to 65535/65536, never 1.0. `normAxis()` in `library/aurora-2d.js`
is the exact form.

`serve --heap-free BYTES` makes the mirror report that much free heap from
`/api/status` instead of the default 0 ("this host has no meaningful number")
— how the editor's capacity warning (docs/webui.md) is exercised against a
starved device without hardware.

| `/api/status` `heap_free` | Live heap margin on the device; `docs/bench-report.md` records the soak's lowest observed value. |

A fence is ~0.5 ms against ~10 µs for the flash read it wraps, so this is how you measure what an operation actually costs in flash ops: read it, run the operation, read it again. Finding that one 650-byte `POST /api/patterns` cost 81,143 of them is what fixed Gitea #292. |
| `/api/status` `frame_us` / `vm_us` / `pipe_us` / `out_us` / `out_fps` | Per-stage frame timing (Gitea #260): average µs per rendered *pattern* frame over the last second — whole engine branch, VM `Engine::frame`, output pipeline (+ the preview copy where there is one), and driver `write_frame` respectively. `tools/hw-bench.mjs` records the four timers next to `fps`. Only pattern frames are averaged, so they read 0 while DDP/E1.31 live input drives the strip. **On a pipelined board** (HUB75 panels, Gitea #306) the stages no longer nest: `frame_us` is the render period on core 1, `pipe_us`/`out_us` come from the output task on core 0, and `out_fps` — frames actually written to the wire, 0 on every other board — is the rate the panel actually showed. `fps` there is the *render* rate and can run well ahead of it; quote both. |

## Host benchmarking

| tool | what it does |
|---|---|
| `tools/pairbench.mjs [--pixels N] [--grid WxH] [--frames N] [--rounds N] [--luxel PATH] [--json PATH] [--labels a,b] a1.js b1.js [a2.js b2.js …]` | **A/B throughput for PAIRS of patterns that render the same thing two ways** — written for the `renderFrame` bulk-op evaluation (docs/bulk-render.md), where the question is "how much does the native op save?" rather than "did the interpreter regress?". Files are consumed two at a time (baseline first); both sides run back to back inside every round and the **best** run of each is reported, because host `luxel bench` on this box has 6–19 % run-to-run spread and throughput noise only ever costs time, so the max is the least biased estimator (.claude/rules/vm-bytecode.md). Prints a markdown table of px/s, ns/px and the ratio; `--json` also writes the rows. Treat anything inside ±3 % as noise, and remember host numbers **understate the device win ~3×** (the Xtensa per-pixel render entry is 317–440 cycles; x86's is nanoseconds) — it is not a substitute for `patbench.mjs` on real hardware. Needs a built `target/release/luxel` (`--luxel` points it elsewhere, e.g. a `--features profile` build). |

## JIT backend gates (`crates/luxel-jit`, Gitea #651)

Plain `cargo test`, no device and no QEMU — `nix develop --command cargo
test -p luxel-jit` runs all four. They are phase 3's entry criteria
(docs/jit-design.md §7.1): nothing goes near the Seengreat until they are
green, because a codegen bug on metal is a crash on core 1 → watchdog
reboot, on a board without serial.

| gate | what it does |
|---|---|
| `cargo test -p luxel-jit --test objdump` | **The encoder gate.** Emits all 150 forms `xtensa::Asm` can produce into a buffer and disassembles it with the devshell's `xtensa-esp32s3-elf-objdump -D -b binary -m xtensa -EL`, comparing mnemonic and operands. **Must be the S3 objdump, not `xtensa-esp-elf-objdump`** — the generic build is for an unknown Xtensa configuration, so its instruction LENGTHS are not ours and it desynchronises (it reads `entry a1, 32` as `excw`). The test refuses to skip if no objdump is on PATH; run it inside `nix develop`. Caught four wrong encodings on its first run — see §7.1. |
| `cargo test -p luxel-jit --test library_diff` | **The differential gate, and the one that matters.** Compiles every `library/*.js`, runs init, `beforeRender` and eight pixel indices of `render*` through the ISA model in `tests/isa/` with a REAL `Vm` behind the context, and compares `Vm::pixel`, `Vm::pixel_written`, every global and the error verdict against the interpreter, bit for bit. Errors are compared down to the message, function index, word index and source position. A `callx8` to a helper or a builtin wrapper traps out of the model and the harness (`tests/common/bridge.rs`) marshals the register and memory state into a real Rust call — that bridge is what makes the whole backend testable on x86. **~2–4 min in a debug build**; it is an interpreter running an interpreter. A mismatch is a bug in the emitter or in the model, never an acceptable difference. |
| `cargo test -p luxel-jit --test isa_selftest` | The ISA model's own 29 tests: every arithmetic and shift form against a Rust reference, the `entry`/`callx8`/`retw.n` window contract two levels deep, the native-call marshalling contract, and that nothing writes the 16-byte window save area. Run it when `xtensa.rs` changes — if the model and the objdump-pinned encoder ever disagree, the encoder is right. |
| `cargo test -p luxel-jit --test golden` and `--test compile_all` | `golden` pins the image size, pool length, function count and an FNV-1a digest for five patterns, and prints the fresh values ready to paste when one changes. `compile_all` compiles the whole library and asserts nothing is refused, that every entry is 4-aligned and outside the pool, and that moving `Env::code_base` changes only the function-address literals. Both print the library-wide code-size totals the device's per-image caps are sized against. |
| `cargo test -p luxel-jit --test alloc_peak` | **The bookkeeping gate (Gitea #665) — how much HEAP the emitter's own plans need, measured.** Wraps the global allocator in a counting shim, compiles every `library/*.js` into a pre-allocated buffer, and asserts the peak of LIVE bytes fits `words × 24 + fns × 240 + 1024` per program (plus a 96 KB ceiling on the worst pattern, so a regression shows up as a number and not only as a rule failure). `ALLOC_PEAK_CSV=1` prints the per-pattern rows and the plan/emit split instead of asserting. **It exists because this is what took the panel down**: `StackMap` was a `Vec` per bytecode word, and a compile beside a resident 4096-px engine ran the heap out mid-plan. `firmware/src/jit.rs`'s `EMIT_PER_WORD` / `EMIT_PER_FN` / `EMIT_FIXED` are the same three constants applied to the heap the device actually has, before it claims any exec memory — **if this test's rule moves, move theirs in the same commit**. Host bytes, so it overstates the device by roughly a third: safe, not tight. |

| `python3 tools/fonts/bdf2psf2.py [--width W] [--height H] <in.bdf> <out.psf>` | **The font converter.** Turns a BDF into the PSF2 blob `crates/luxel-core/src/text.rs` `include_bytes!`s: a 32-byte header then 95 glyphs (ASCII `0x20..=0x7E`, in order, no Unicode table) of MSB-first row-packed rows, so lookup on device is `codepoint - 0x20` times `charsize`.
